## What was investigated

The report showed two related but distinct failure paths after a Windows Codex update:

1. Registered Core bootstrap/setup could fail before the service created the ownership receipt needed for readiness.
2. An already-running execution process could continue failing after a fresh package-context process reported `ready`.

They were kept separate so one patch would not overclaim or hide the second lifecycle problem.

## Finding 1 — bootstrap dependency

**VERIFIED IN CURRENT SOURCE**

Current `main` resolves the active Windows sandbox permission profile before calling the Registered Core service provisioning path. A Full Access / unrestricted profile is intentionally not enforceable by the Windows sandbox, so the setup path can fail before the service creates the Registered Core ownership receipt.

The fork patch changes only that bootstrap decision:

- managed restricted profiles are still validated;
- Registered Core bootstrap may proceed to service provisioning when the current profile itself is unenforceable;
- non-Registered-Core behavior remains unchanged.

Regression coverage was added for both Registered Core and legacy behavior.

Engineering analysis was published directly on the issue:

- [Bootstrap analysis and proposed fix](https://github.com/openai/codex/issues/47555#issuecomment-5796347506)
- [Patch/branch handoff](https://github.com/openai/codex/issues/47555#issuecomment-5796497059)

## Finding 2 — stale package-generation process

**SOURCE-TRACED; lifecycle patch not yet justified in this public repository**

The Registered Core installation record is reread from the protected registry rather than held as a simple in-process cache.

The service also intentionally authenticates Registered Core provisioning clients against the currently installed package generation. An old `codex.exe` or `codex-code-mode-host.exe` surviving an app update must not be allowed to provision or refresh the new package generation.

That changes the recovery model:

**old package process → cannot safely self-refresh → must be retired/replaced → fresh process consumes new Registered Core state**

This is a security boundary, not a restriction to bypass.

Published source-trace notes:

- [Registry/readback investigation](https://github.com/openai/codex/issues/47555#issuecomment-5796775622)
- [Complete lifecycle-fix handoff](https://github.com/openai/codex/issues/47555#issuecomment-5796821816)

The remaining implementation question is which desktop lifecycle component owns the package-generation transition and should invalidate/restart an existing execution host after update or successful sandbox setup.
