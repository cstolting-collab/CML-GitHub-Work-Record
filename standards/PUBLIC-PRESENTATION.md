# Public presentation standard

## Purpose

Make the public account understandable to a reviewer without requiring knowledge of internal project language.

## Profile

- Use a complete opening summary and a small set of linked starting points.
- Keep a public project directory separating original repositories, engineering records, demonstrations, and upstream forks.
- Include only public destinations in the visitor navigation.
- Preserve a clear route from a project to its documentation and evidence.

## Repository landing pages

State the purpose, maturity, supported setup, validation command, documentation entry points, and license. Use commands present in the current source or existing maintained documentation.

Preserve material limitations. A documentation cleanup must not broaden the implementation contract.

For forks, identify the upstream project and original author prominently. Retain upstream licensing and attribution. Distinguish the fork's contribution from the upstream product.

## Evidence and tone

Use direct, factual language. Avoid alarmist comparisons, unsupported claims, estimated time-to-run promises, invented credentials, and promotional test badges without matching evidence.

Keep dated results explicitly historical. Never describe a prior head as the current head or a fork pass as upstream acceptance.

## Validation before publishing

Check file content, relative links, repository visibility, executable names, and license consistency. Separate documentation checks from runtime tests; report only what was actually checked.

## Organization changes

Preserve Git history and dated evidence. Archive only repositories authorized by the owner. Do not rename repositories, delete branches, or change visibility merely to improve presentation.

Repository descriptions, topics, profile pins, and archive status are separate settings. Editing a README does not change them. Record blocked settings actions and the next actor explicitly.
